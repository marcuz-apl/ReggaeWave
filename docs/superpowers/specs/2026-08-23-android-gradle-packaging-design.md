# Android Gradle Packaging Design

**Status:** Approved for local implementation; no remote push or release action is authorized.

**Product decision:** The product owner approved Android packaging as an exception to the
native-client exclusion in `docs/PRD.md`. This change creates installable development and
CI artifacts only. It does not add Play Store distribution, signing keys, analytics,
network services, or user-media collection.

## Goal

Package the existing JUCE mobile source as an installable Android application that produces:

- debug APKs for Windows Android Emulator (`x86_64`) and physical Android devices (`arm64-v8a`);
- release APK and AAB artifacts for `arm64-v8a` in CI;
- a versioned, reproducible Android Studio/Gradle project that does not publish artifacts itself.

## Decision

Use JUCE's Projucer Android Studio exporter for the Android application boundary. JUCE's
official CMake documentation states that Android targets are not currently supported, while
the Projucer supports Android Studio export. The existing top-level CMake project remains
the desktop and test build system; it is not used to create the installable Android app.

`apps/mobile/ReggaeWaveMobile.jucer` becomes the source project definition for the Android
export. The generated Android Studio project, Gradle wrapper, manifest, Java activity/JUCE
glue, resources, and native build files live below `apps/mobile/Builds/Android/` and are
tracked so CI and Windows developers use the same project. Regenerate that export whenever
the `.jucer` definition changes and review the resulting Gradle diff.

## Components and Responsibilities

| Path | Responsibility |
| --- | --- |
| `apps/mobile/ReggaeWaveMobile.jucer` | Mobile target metadata, Android exporter settings, source membership, modules, icons, permissions, and ABI configuration. |
| `apps/mobile/Builds/Android/` | Generated Gradle project consumed by Android Studio and CI. Contains the Android manifest, wrapper, Java/JUCE activity glue, and native build integration. |
| `apps/mobile/Source/` | Existing shared JUCE mobile UI and platform bridges. No Android-only product logic moves into Gradle Java code. |
| `.github/workflows/build-and-release.yml` | Runs Gradle package tasks and uploads APK/AAB artifacts from the generated project. |
| `tests/android/` | Packaging-contract checks that assert the Gradle project declares the expected application id, minimum SDK, ABI set, and APK/AAB output paths. |
| `README.md` and `docs/note-0005-mobile-edition-architecture-testing-and-roadmap.md` | Accurate developer instructions and artifact descriptions. |

## Application Contract

- Application id: `com.alfazen.reggaewave`.
- Product name: `ReggaeWave`.
- Minimum Android API: 29, matching the API floor required by the currently pinned JUCE Android font implementation.
- Debug ABI set: `x86_64` and `arm64-v8a`; this supports the fastest Windows emulator path and physical-device testing.
- Release CI ABI set: `arm64-v8a`.
- Debug builds use the standard local Android debug keystore generated by Android tooling.
- Release builds are unsigned unless a separately authorized CI secret-backed signing configuration is supplied. Keystores, passwords, `local.properties`, and machine SDK paths are never committed.
- The Gradle project must package the JUCE-generated Android activity and native library into the APK/AAB. A loose `.so` is not a release artifact.

## Build and Test Flow

1. A Windows developer opens `apps/mobile/Builds/Android/` in Android Studio after installing Android SDK Platform 29 or later, Build-Tools, NDK r26b, CMake, and an `x86_64` emulator image.
2. Android Studio runs the Gradle debug task, producing an installable universal debug APK containing both supported debug ABIs.
3. The developer installs that APK onto the `x86_64` emulator or connects an `arm64-v8a` Android phone with USB debugging enabled.
4. CI invokes Gradle directly, verifies that the native app packages successfully, and uploads the ARM64 release APK and AAB as artifacts.
5. CI fails if either expected package type is absent. It must not silently substitute a `.so` file for an APK/AAB.

## CI and Release Behavior

- Pull requests and branch pushes run Android Gradle packaging verification but do not publish a GitHub release.
- Version tags collect the APK/AAB alongside existing desktop and iOS artifacts.
- Android artifact names include the root `VERSION` identifier and ABI.
- GitHub releases contain installable APK/AAB files only after the Gradle verification succeeds.
- Store submission remains out of scope; no Play Console credentials or upload actions are added.

## Failure Behavior

- Missing Android SDK, NDK r26b, or CMake produces an actionable local setup error.
- A missing generated Gradle project or Gradle wrapper fails CI before native compilation.
- Missing APK/AAB output fails the packaging job, even when native compilation produces a `.so`.
- Android emulator ABI mismatch is reported as a test-environment issue; users select `x86_64` for Windows emulator testing or use an ARM64 physical device.
- Signing failures are isolated to release-signing configuration and do not prevent debug APK generation.

## Verification

- A packaging-contract test first fails while the Gradle project is absent.
- The generated project passes that contract only when it has a manifest, Gradle wrapper, expected application id, API 29 minimum, and both debug ABIs.
- `gradlew :app:assembleDebug` produces an APK containing `x86_64` and `arm64-v8a` native libraries.
- `gradlew :app:bundleRelease` produces an ARM64 AAB without requiring committed credentials.
- CI validates the package presence before uploading artifacts.
- Existing C++ unit tests continue to run unchanged.

## Rollback

Remove the tracked Projucer Android export, Gradle CI steps, package checks, and Android-specific documentation. The existing desktop CMake build and iOS Simulator workflow remain independently usable. No data migration or server contract rollback is required.
